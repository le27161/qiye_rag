# 简历模板三：后端开发与知识库数据治理工程师

## 项目名称

**KnowForge RAG 平台：后端服务架构与知识库治理**

## 项目周期

20XX.XX - 20XX.XX（按实际经历填写）

## 项目背景

企业 RAG 系统的难点不只是“把文档切块写入向量库”，还包括多格式资料解析、知识库版本管理、增量入库、数据隔离、质量报告、回滚和线上查询稳定性。KnowForge 将离线入库与在线问答拆分：离线链路负责资料治理和版本构建，在线链路只查询当前 active `kb_version`，从而降低知识库更新对线上服务的影响。

## 核心功能

### 一、后端服务架构

1. **FastAPI API 层**：提供问答、历史、反馈、知识库版本、管理状态、健康检查和静态页面路由。
2. **WebSocket 流式问答**：按事件返回状态、Token、引用来源、诊断信息和错误信息，支持前端实时渲染。
3. **请求上下文管理**：通过 `QueryServiceContext` 管理 query、history、session、source、DataScope、场景和知识库版本。
4. **Preflight 检查**：启动前校验环境变量、模型路径、Milvus、MySQL、场景配置和 active 知识库版本。
5. **权限与运行保护**：支持管理令牌、API Key 依赖、CORS、限流和统一异常响应。

### 二、知识库治理

1. **多格式 Loader Registry**：统一加载 Markdown/TXT、PDF、DOC/DOCX、PPT/PPTX、CSV/XLS/XLSX，并把表格行转换为结构化 Document。
2. **父子分块策略**：子块用于精确召回，`parent_content` 保留完整上下文，最终构建 Prompt 时按父块去重和截断。
3. **IndexManifest 增量机制**：基于文件 fingerprint（路径 + 修改时间纳秒 + 大小，不读文件正文）、embedding 版本和 chunk schema 严格等值匹配，判断未变化文件是否跳过、引用复用或重建。
4. **引用式增量构建**：跨版本增量时不复制 Milvus 行、不重新 embedding，而是通过 `valid_from_seq` / `valid_to_seq` 有效期窗口复用旧 chunk 的可见性，在 MySQL manifest 和 chunk_version_index 登记引用关系。文件变化时只设 `valid_to_seq` 收口，不删 Milvus 行，保证回滚时数据不丢。
5. **MySQL 版本控制面**：使用 `kb_versions` 和 `kb_active_versions` 存储版本状态、active 指针、单调 `version_seq`、模型版本和入库统计。`version_seq` 用于文档检索的有效期窗口过滤，`kb_version` 用于 FAQ 快照精确匹配。
6. **版本激活 7 步事务**：`activate_version` 在单事务内完成 FOR UPDATE 锁定 active 指针 → 判别激活/回滚 → 旧 ACTIVE 改 STAGED → 目标设 ACTIVE → 更新指针（previous_kb_version 支持快速回滚）→ 写激活/回滚流水 → 推进缓存 epoch 使旧检索缓存失效。
7. **质量报告与门禁**：激活前生成入库质量报告（不写 Milvus，只解析和切分），门禁分两组：11 个数量阈值类（默认全 0，OCR 风险写死 0 不允许放宽）+ 4 个存在性必填类。门禁失败直接 `sys.exit(1)` 阻断激活。
8. **DataScope 隔离**：入库时写入 tenant、dataset、visibility、allowed_roles，检索时统一生成 Milvus 过滤表达式。
9. **父子切分策略**：表格行/已复核 OCR 不切分（整行作为唯一块）；Markdown 先按 `#/##/###` 标题切分再递归切分；普通文本走父子切分（子块精准匹配，`parent_content` 保留父块全文作为上下文）。`chunk_id` 纳入 `kb_version` + `embedding_model_version` + `chunk_schema_version`，保证同一文件在两个版本里可以同时存在不冲突。
10. **OCR 离线治理**：扫描件先进入 OCR 输出目录，人工确认 Markdown 后再放入对应业务 source 目录重建知识库。

## 个人职责

- 负责 FastAPI 后端服务结构设计，完成 API 路由、WebSocket 问答、健康检查、管理状态、知识库版本接口和异常处理。
- 设计离线入库服务 `IndexingService`，实现目录遍历、source 推断、文件加载、元数据标准化、分块、Milvus 写入和 manifest 更新。
- 实现多格式文档加载注册表，支持文档、表格和 OCR 后文本进入统一入库链路。
- 设计并实现父子分块策略，将 `parent_content`、`parent_id` 和 `chunk_id` 写入 metadata，兼顾精确召回和上下文完整性。
- 将知识库版本元数据从文件式存储迁移为 MySQL 控制面，支持 active 指针切换、历史版本保留和版本状态查询。
- 实现引用式增量入库：未变化文件不复制 Milvus 行、不重新 embedding，通过 `valid_from_seq` / `valid_to_seq` 有效期窗口复用旧 chunk 可见性，在 MySQL manifest 和 chunk_version_index 登记引用关系；变化文件设 `valid_to_seq` 收口后重新入库，不删旧 Milvus 行保证回滚不丢数据。
- 设计 DataScope 数据隔离模型，在入库和查询两端统一处理 tenant、dataset、visibility 和 allowed_roles。
- 编写入库质量报告和门禁脚本，确保候选版本未通过质量检查时不会被激活。
- 编写 Docker Compose 和运行检查脚本，保证 MySQL、Milvus、MinIO、etcd、API 等服务可复现部署。

## 项目成果

- 搭建了从“多格式资料解析”到“active 版本上线查询”的完整知识库治理闭环。
- 将知识库版本管理沉淀到 MySQL，线上查询通过 `version_seq` 有效期窗口（文档）和 `kb_version` 精确匹配（FAQ）过滤当前 active 版本，降低错误版本污染线上结果的风险。
- 通过 IndexManifest 支持同版本跳过未变化文件和跨版本引用式增量（不复制 Milvus 行，只改有效期窗口 + 登记 MySQL 引用关系），减少重复 embedding 成本。
- DataScope 隔离模型使多租户、多数据集和可见性过滤成为统一能力，而不是散落在业务代码中的条件判断。
- 入库质量门禁可在版本激活前发现空文件、重复 FAQ、非法 source、OCR 风险和 FAQ/文档冲突等问题。
- 实际简历中建议补充自己的指标：处理文件数量、chunk 数、增量复用比例、入库耗时、质量门禁拦截次数。

## 简历使用建议

- 不要写"Milvus Alias 原子切换版本"，本项目版本切换核心是 MySQL active 指针 + `version_seq` 有效期窗口过滤（文档）和 `kb_version` 精确匹配（FAQ）。
- 可以写"父子分块"，但要说明三种切分策略：表格行/OCR 不切、Markdown 按标题切、普通文本父子切。子块召回、`parent_content` 回填父块上下文。
- 不要写"跨版本复制向量"，本项目是引用式增量：不复制 Milvus 行，通过 `valid_from_seq` / `valid_to_seq` 有效期窗口复用旧 chunk 可见性。
