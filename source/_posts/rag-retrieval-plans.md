“Wi-Fi 密码在哪里看”和“对比两个采购制度的适用范围”，即使进入同一个知识库，也不该使用完全相同的检索预算。前者很可能有标准 FAQ，后者则需要多份材料。把所有问题固定成 Top-20，只是把决策藏进了一个默认值。

<!-- more -->

## 在调用数据库前，先形成一份计划

检索计划描述这次请求允许查哪些资料形态、各取多少候选、是否生成查询变体、是否重排，以及允许什么样的 FAQ 快速返回。

它不是检索结果，也不是权限范围。权限回答“哪些数据可以看”，计划回答“在可看的数据里怎样找”。两者应分别计算，再一起交给检索执行层。

例如，标准 FAQ 倾向可以减少文档候选，但不必完全禁用文档兜底；综合问题可以扩大候选和上下文预算；追问需要先补足上下文，不能因句子短就被当成简单 FAQ。

## 风险保护应当单调收紧

金额、合规和表格字段不一定是独立的主意图，而是叠加约束。一句“某岗位差旅额度是多少”，既可能是 FAQ，也可能涉及金额和表格。

一种可维护的实现方式，是先建立基础计划，再逐项施加保护：

```python
from dataclasses import dataclass, replace

@dataclass(frozen=True)
class Plan:
    doc_top_k: int = 12
    context_limit: int = 4
    exact_faq_only: bool = False
    reasons: tuple[str, ...] = ()

def guard_high_risk(plan: Plan) -> Plan:
    return replace(
        plan,
        doc_top_k=max(plan.doc_top_k, 24),
        exact_faq_only=True,
        reasons=plan.reasons + ("high_risk_guard",),
    )
```

数字仅为示例。关键不在 24，而在 `max` 与显式保护：后续普通规则不应把高风险预算覆盖回较小值，也不该意外重新允许模糊 FAQ 直出。

## 候选数量和上下文数量不是同一个参数

扩大召回候选可以减少漏检，但不代表全部送进 Prompt。候选预算决定重排前能看到多少内容，上下文预算决定最终向模型提供多少证据，两者影响不同阶段的成本。

假设正确片段已经进入候选集，却在最终组装时被重复父块挤掉，继续增加 `doc_top_k` 可能毫无帮助。应该检查重排、去重、多样性和 token 预算。

类似地，FAQ 直出阈值只对其所对应的分数契约有意义。不能把某个重排模型的阈值，直接迁移到混合检索分数上。

## 调参从失败类型出发

高风险 FAQ 被误直出，优先收紧直出条件；正确资料根本没进入候选，先查资料、过滤和查询，再考虑扩大召回；首 token 延迟升高，先拆阶段耗时，而不是立即减小所有 Top-K。

每次调整应保存旧配置、评测集版本和分组报告。除了总体均值，还要看短问句、追问、编号、表格和高风险问题是否退化。

计划最终应留下可读原因，例如“知识综合查询 + 表格优先 + 高风险保护”。这样一次错误可以追溯到哪条规则生效，而不是只能看到一堆事后无法解释的数字。
