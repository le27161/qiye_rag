一个助手能回答“库存不足怎么办”，和它能直接创建采购单，是两种不同的产品。前者主要影响信息，后者会改变业务状态。Agent 值得讨论的地方，不是对话变得多像人，而是模型开始参与行动后，系统怎样约束这种能力。

## 先看谁在决定下一步

在固定工作流里，程序预先规定路径：提取条件、查数据库、整理结果。模型可以负责其中某一步，但不能自行增加一个“给供应商发邮件”的动作。这样的设计仍然可能有智能判断，只是判断发生在有限范围内。

更自主的 Agent 会根据当前结果决定接下来调用哪个工具、是否继续查证、什么时候结束。它适合路径不容易预先枚举的任务，也意味着调用次数、时间和结果更难预测。两者不是非此即彼：可以把大部分流程固定，只在选取候选表、判断问题是否完整等局部环节交给模型。

行业对 Agent 的定义并不完全统一。与其争论某个系统“算不算”，不如写清楚它有哪些决策权。一个受限的问数系统，也可以被称为问数 Agent，但不必因此把它描述成能自由规划所有数据分析任务的通用代理。

## 工具调用是一份申请，不是一张通行证

模型输出一个工具名称和参数，意味着它提出了行动请求。真正的程序仍要检查工具是否在允许列表里、参数是否有效、当前用户是否有权执行，然后才调用外部服务。工具返回的内容也不天然可信：网页、文档和数据库备注里都可能夹带诱导指令。

例如“查看华东订单”应携带服务端确定的用户身份和数据范围，而不能让模型自己填写一个管理员角色。若工具能够修改订单，除了权限还要考虑确认、幂等键和审计。对话里出现“已确认”几个字，不能替代一次可靠的授权记录。

读数据的工具与写数据的工具最好分开设计。问数系统只需要只读能力，就不要顺便向它开放数据库管理接口。最有效的限制往往不是在提示词里多写一段警告，而是让危险动作根本不在可调用范围内。

## 确定性流程是模型能力的支架

设想一个请求：“看看上个月退货比较多的品类。”模型擅长把这句话转成候选分析意图，但“退货多”究竟按数量还是金额排序，需要澄清或引用已公示的默认规则。获得明确口径后，日期计算、权限筛选、指标公式和结果截断应尽量由程序落实。

这不是削弱模型，而是让它集中处理模糊语言。把所有东西都交给模型，每一次回答都可能重新解释规则；把每一个词都写死，又失去了自然语言入口的意义。合理分工通常是：模型处理语义候选，程序管理约束与执行，用户决定关键歧义。

类似地，多 Agent 只有在职责隔离、独立上下文或并行探索确实有收益时才值得引入。把同一条问数链拆成多个角色，可能只增加消息传递、成本和责任追踪难度。一个清晰的状态图未必比一群互相讨论的角色缺少能力。

## 结束条件也属于系统设计

一个系统如果只知道“继续尝试”，就很容易在错误 SQL、过期元数据或网络超时上反复消耗。开始任务时应同时定义结束条件：预算耗尽、相同错误重复、关键条件缺失、权限不满足，以及结果已经足够回答。

失败还需要分类。临时网络错误可以在剩余时间内重试；指标口径不明应该向用户澄清；越权访问必须拒绝，不能把拒绝信息发给模型后鼓励它换个写法绕过去。重试是恢复机制，不应变成寻找安全规则漏洞的机制。

所以，评估 Agent 不只是看完成率，还要看它是否在该停的时候停下、是否需要不必要的工具调用、是否把不确定结果包装成确定事实。对真实业务而言，这些能力往往比更长的自主推理过程更重要。
