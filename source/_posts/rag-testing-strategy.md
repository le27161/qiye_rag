每次改一条路由规则，都启动数据库、本地模型和云端 LLM，再人工问几句，既慢也难定位。RAG 的确有概率性输出，但权限、过滤、策略选择和事件状态机，大量逻辑都是确定的，不应被模型的不确定性拖累。

<!-- more -->

## 先测试不该随机的部分

规则路由、source 白名单、Prompt Profile 优先级、缓存键、版本可见性和上下文去重，都适合用小输入直接测试。

例如 [版本发布](/rag/ingestion-and-versioning/) 中的半开有效期，可以独立验证：

```python
import pytest

def is_visible(start, end, active):
    return start <= active and (end == 0 or active < end)

@pytest.mark.parametrize(
    "start,end,active,expected",
    [(1, 2, 1, True), (1, 2, 2, False), (2, 0, 2, True)],
)
def test_version_window(start, end, active, expected):
    assert is_visible(start, end, active) is expected
```

这段测试不需要数据库和模型。它也明确了版本边界包含哪一端，避免不同模块各自解释。

## Fake 负责可控，真实集成负责可信

模型调用可以用 Fake 返回固定片段，向量库可以用小候选集模拟命中、空结果和异常。这样能稳定测试 Pipeline 分支、失败收尾和流式协议。

但 Fake 无法证明 SDK 参数正确、Milvus 表达式可执行、BM25 分词已配置，也无法证明数据库 schema 可用。对应能力还要有少量真实集成测试，检查字段、索引、过滤、读写及事务行为。

特别是 wrapper 自动建 schema 时，应测试实际结果，而不只是 mock 了一个调用后确认函数被执行。

## 安全测试要包含反例

只测“合法用户能看到自己的文档”不够，还应测试看不到别人的文档；非法 source 被拒绝；无令牌不能访问管理接口；请求自报管理员角色不生效；缓存不能跨权限复用。

过滤字符串测试之外，还应在真实小集合执行恶意引号、反斜杠和空范围用例，确认不会扩大数据可见性。

限流测试最好注入可控时钟，不要依赖长时间等待。多副本环境则需要另外验证限流状态是否共享，进程内测试通过不代表集群限流正确。

## 流式接口有自己的状态机

测试不只检查是否收到若干 token，还要确认一个请求只有一个明确终态、事件带正确请求 ID、错误后前端能停止等待，以及最终全文与持久化记录一致。

还应覆盖客户端断开、慢客户端、底层超时和生成器关闭。业务层把异常转成脱敏事件，不能导致服务端丢失失败日志，也不能把 API Key 或数据库连接串透传给浏览器。

## 代码验收与质量评测分开报告

测试通过说明程序遵循了预期契约，并不证明真实模型更会检索或回答。反过来，一组模型评测进步，也不证明权限隔离没有被破坏。

持续集成可以先跑快而稳定的纯逻辑测试，再跑依赖服务的契约与集成测试，最后执行少量真实问答冒烟和固定数据集评测。使用哪些依赖、跳过哪些检查，都应明确记录；未配置密钥导致的跳过，不能被写成端到端验收通过。

最有价值的测试，是让失败立即指出哪一层的假设被打破，而不是留下一个“最终答案不一致”的大黑盒。
