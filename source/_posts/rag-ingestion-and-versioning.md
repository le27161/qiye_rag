资料更新脚本执行完，没有抛异常，能不能立即给用户使用？不一定。文件可能解析为空，source 可能写错，旧制度可能仍然与新制度同时被召回。入库完成只证明处理过程走到终点，知识发布还需要证明新数据值得接替旧数据。

## 先构建候选版本，最后再切 active

一次更新应明确目标范围、基线版本和配置摘要，然后在候选版本中写 FAQ 与文档，生成质量报告、执行检索回归，最后才允许激活。

控制面保存版本状态和 active 指针，数据面保存可检索文本及版本相关字段。激活只切换指针，可以避免在发布瞬间批量重写全部向量；但它不自动构成跨 MySQL 与 Milvus 的分布式事务。

因此，切换前仍需确认数据写入、索引和查询可见性已经满足要求。请求开始时固定一次版本快照，避免同一回答混用发布前后的证据。

## FAQ 快照与文档增量可以采用不同策略

FAQ 的单位通常是一个标准问题和标准答案，按目标版本重建快照比较直接。查询时使用 `kb_version` 精确过滤，避免返回旧口径。

长文档数量更多，重新解析和编码的成本也更高。引用式增量可以复用未变化文档，只有新增或修改的文件才重新生成片段；删除文件则让旧片段在新版本中不可见。

这两种模式可以共存，但过滤规则不能混用。FAQ 带有统一版本字段，不代表它也使用文档的有效期逻辑。

## 有效期视图怎样解释旧片段

在线性版本序列中，可以给片段设置半开区间：起点包含，终点不包含；`valid_to_seq=0` 表示尚未失效。

```text
valid_from_seq <= 当前版本序号
并且 (valid_to_seq == 0 或 valid_to_seq > 当前版本序号)
```

假设 A 文件保持不变，B 文件在版本 2 更新：

| 片段 | 生效起点 | 失效终点 | v1 可见 | v2 可见 |
| --- | --- | --- | --- | --- |
| A 的旧片段 | 1 | 0 | 是 | 是 |
| B 的旧片段 | 1 | 2 | 是 | 否 |
| B 的新片段 | 2 | 0 | 否 | 是 |

版本 2 不必复制 A 的向量，历史版本 1 仍然看到旧 B。这就是引用式增量节省编码与存储成本的来源。

## 增量判断不能只看一个文件指纹

同一个文件，即使内容没变，解析器、切分策略、Embedding 模型或 metadata 规则变了，也可能需要重建。

Manifest 应同时记录源文件身份、内容或快速指纹、处理配置摘要，以及该版本引用的片段清单。稳定片段 ID 也必须考虑内容修订或版本：不能因复用“路径 + 块序号”，覆盖掉回滚还需要的旧片段。

完整发布还要区分未变化复用、修改重建、新增重建和删除失效，并在报告中分别统计，而不是只输出一个总条数。

## 有效期方案有前提，不支持随意分叉

单一全局序号和一个失效终点，很适合串行、线性发布。但当多个候选版本同时基于同一旧版构建，或回滚到旧版后再分叉发布时，简单区间不一定能表达各分支的继承关系。

这时需要限制构建与发布串行、显式管理基线关系，或改用版本成员映射等方案。不要把“指针可回滚”误解为“任意分支都能无条件增量合并”。

失败候选还可能留下未来失效标记，需要可恢复的构建账本和清理策略。归档旧数据前，也要确认它不再被保留版本引用。

可回滚发布的关键，不是给版本起一个名字，而是让数据可见性、构建记录、质量证据和切换过程保持一致。
