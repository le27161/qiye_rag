问“发生设备故障后，多久内需要上报”，检索结果却只有“出现以下情况时应及时上报：”，真正的时间要求落在下一块。模型并没有凭空变笨，问题可能在入库时就已经形成：系统把一个完整的业务条件切碎了。

## 切块边界先服从资料结构

固定每 N 个字符切一刀，容易把句子、标题和列表拆散。递归切分更温和：先尝试按段落分开，过长时再尝试换行、句号和更细粒度边界。

Overlap 能缓解边界信息丢失，但不是越大越好。重复片段会增加存储、召回重复和上下文成本。切分器配置的长度单位也要核对：字符数、token 数和字节数不是一回事，中文 token 密度尤其不能用固定比例保证。

Markdown 还可以先保留标题层级，再对各节正文细分。标题路径应成为 metadata 的一部分，避免把“例外条件”从它所属的制度和章节中剥离。

## 父子块是在精确性与完整性之间搭桥

小块更聚焦，适合检索；大块包含条件、定义和上下文，适合生成。父子块方案用子块建立检索表示，命中后再回到对应父块。

例如可以从父块约千字符、子块数百字符开始实验，但这只是候选配置。法规、接口手册和操作步骤的最佳边界不一样，应该以实际问题的证据覆盖率为准。

多个子块可能命中同一个父块，因此最终上下文要按父块 ID 去重，并受 token 预算约束。否则“取前五个命中”可能只是把同一段原文重复五次。

父块恢复也必须遵守相同的租户、版本和访问规则。不能子块过滤正确，随后通过一个无约束的 `parent_id` 查询把其他范围的数据补回来。

## 表格行是一种业务记录

表格中的“1500”没有表头，就不知道是金额、数量还是日期。把表格直接拼成普通长文本再递归切分，可能把字段名和值拆开，甚至把相邻记录的条件拼到一起。

对清单和台账，可以把每一行序列化成带字段名的文本：

```text
文件：设备维护标准.xlsx
工作表：现场处理
Excel 行号：7
设备类型：便携终端；故障等级：二级；上报时限：30 分钟；适用区域：华东
```

metadata 同时保存文件、工作表、物理行号、字段值和权限信息，方便筛选与引用。示例中的制度与数值仅用于说明结构，不代表真实业务规定。

实际表格还要处理合并单元格、多行表头、单位、脚注和公式。不能无条件向下填充所有空值；公式读取到的缓存结果也可能过期。跨行汇总或精确算术，往往更适合结构化查询，而不是纯语义检索。

## 解析增强不能省略质量检查

普通文本层 PDF 可以用轻量解析；扫描件、多栏或复杂版面则可能需要 Docling、OCR 或其他增强路径。解析器负责恢复文本和结构，不负责判断资料是否适合发布。

转换结果应保留页码、标题、表格和原始文件对应关系。OCR 把“不得”识别成“得”，可能改变整个条款含义；图中文字转成文本，也不等于系统已经具备完整的多模态推理能力。

切分质量最好抽样看真实片段：开头能否知道主题，结尾是否留下半个条件，引用能否回到原位置。检索质量的上限，很大程度上由这些不起眼的数据处理决定。
