一个回答写得完整、语气专业，仍然可能引用了旧制度。另一个回答只有两句话，却准确指出当前资料没有相关规定。只凭“看起来不错”评估 RAG，容易奖励最会表达的错误。

<!-- more -->

## 质量要分三层看

第一层是资料与入库质量：文件是否读到了有效内容，切块是否破碎，来源字段是否正确，FAQ 与正文是否冲突。

第二层是检索质量：在正确版本和权限下，目标证据有没有进入候选，排序是否靠前，筛选后是否仍然保留。

第三层才是答案：是否忠于证据、保留条件、正确引用，以及该拒答时有没有拒答。把这些问题压成一个总分，会丢掉修复方向。

## Recall 和 MRR 各自在看什么

若某问题有两条标注相关证据，Top-5 只找回一条，则按相关文档集合定义的 Recall@5 为 `1/2`。如果报告统计的是“至少找回一条的样本比例”，更适合明确称作 Hit@K，不能与上述定义混用。

MRR 只关心第一条正确证据的位置。两个问题的首条相关证据分别排第 1 和第 4，MRR 为：

```text
(1/1 + 1/4) / 2 = 0.625
```

它能反映正确证据是否靠前，但无法衡量第二、第三条必要证据有没有被覆盖。跨文档总结和条件比较，需要额外观察完整证据覆盖。

关键词覆盖可以做低成本信号，但答案同时出现“允许”和“不允许”，仍然可能命中同一关键词。数字、否定和适用条件最好有更明确的检查。

## 样本要描述边界，不只有问题和答案

一条有用的评测记录可以是：

```json
{
  "id": "maintenance-014",
  "question": "ZX-410 的 E207 是否适用旧版处理流程？",
  "scenario": "device_support",
  "kb_version": "candidate-20261026",
  "scope_fixture": "authorized-technician",
  "expected_sources": ["maintenance"],
  "relevant_document_ids": ["zx410-firmware-policy"],
  "expected_behavior": "explain_version_boundary",
  "risk_group": "versioned_identifier"
}
```

示例不是现成可执行数据集。真实记录还需明确资料与标注版本；对追问保留必要历史；对无权限或无资料样本标注正确拒答行为。

## 总体进步，可能掩盖关键组退化

某次调参让大量普通 FAQ 更快，却让少量费用问题出现误直出，总均分仍可能上升。因此门禁需要按场景、风险、追问、表格和无答案样本分组。

阈值应由业务损失和稳定基线确定，不是从教程里挑一个“行业标准”。在固定样本上做配对比较，报告样本量、失败列表与配置摘要，通常比单个百分比更有判断价值。

LLM 裁判或 RAGAS 类工具可以补充语义评价，但应记录裁判模型、提示词与版本，并用人工样本检查偏差。它们不是天然真值，敏感资料也不能未经审批就发送给外部评测服务。

## Bad Case 是一个待验证假设

线上出现错误后，先保存脱敏现场与版本信息，再判断是误路由、改写漂移、错误过滤、漏召回、重排失败、上下文遗漏还是生成失真。自动归因可以给候选结论，人工复核再确认。

确认问题后，把样本加入回归集，做最小修复，然后重跑该组和全局门禁。仅修改最后一句 Prompt，可能掩盖真正的入库故障。

改进闭环的终点不是“这次答对了”，而是同类问题被纳入可重复验证，并且其他能力没有被悄悄改坏。
