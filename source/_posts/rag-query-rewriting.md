用户先问“正式员工申请远程办公需要满足什么条件”，接着问“那外包人员呢”。第二句话放在聊天里很清楚，单独交给向量库却没有完整主题。解决这个问题，不是无条件把所有历史拼进检索，而是准确恢复这一次追问省略了什么。

<!-- more -->

## 改写只补上下文，不替用户做决定

合理的独立查询可以是“外包人员申请远程办公需要满足什么条件”。它保留业务动作，替换适用对象，没有擅自增加申请期限或审批人。

错误改写则可能变成“外包人员是否禁止远程办公”。这已经把未确认的结论写进查询，会让检索和后续回答共同偏向某个答案。

因此，原始问题与改写问题应同时保存。必要时展示简短确认；找不到足够历史时，询问用户指的是哪项业务，比猜测一个对象更安全。

## 完整问题往往不需要改写

当用户明确说出制度名称、适用时间和对象，再调用一次 LLM “润色”，可能删掉关键限定词，也会增加一次串行等待。

改写应有触发条件，例如存在指代或省略，且有可用历史。系统还应识别话题切换：“另外，网络证书如何更新”不应继续继承远程办公的主题。

一个适合记录的中间对象是：

```json
{
  "original_query": "那外包人员呢？",
  "standalone_query": "外包人员申请远程办公需要满足什么条件？",
  "rewrite_used": true,
  "history_message_ids": ["m17", "m18"],
  "warnings": []
}
```

这些字段用于诊断，不应把完整历史和敏感信息无差别传给前端或外部观测平台。

## 查询变体是另一个问题

改写解决“问的是什么”，变体解决“资料里可能怎么说”。例如完整查询还可以生成“外协人员远程办公准入要求”，帮助匹配不同术语。

变体必须保留型号、时间、金额和适用人群等实体约束。通常应保留原始或补全查询，控制额外变体数量，并去重。如果每个变体都各召回一大批候选，数据库负载和重排成本很容易成倍增加。

局部同义词规则可以先覆盖稳定术语；更开放的表达再考虑模型生成。是否启用，应由真实漏召回样本证明，而不是因为“多查几次总会更好”。

## 历史压缩要承认有损

摘要加最近消息，可以控制输入长度，但摘要可能遗漏否定条件或数字。为关键实体保留明确字段，比单靠一段自然语言总结更稳妥。

还要区分“消息条数”和“对话轮数”：一轮通常包含用户与助手两条消息。配置写成最近 8 条消息，就不应在文档里解释为最近 8 轮。

异步刷新摘要时，需要记录摘要覆盖到哪个消息 ID，并避免旧任务覆盖新摘要。历史中的用户指令和模型回答也不能当作已核实制度；历史用于理解问题，权威事实仍应来自当前授权知识。

改写效果应独立评测：对象是否保留、主题是否正确、是否凭空增加条件，以及最终召回是否真的改善。这样才能区分“改写成功”与“句子读起来更顺”。
