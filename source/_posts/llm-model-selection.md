选模型时最容易比较的是参数和榜单，最难比较的是“放进自己的系统之后是否值得”。同一个模型可能很会写长文，却不擅长遵守工具参数；单次回答便宜，也可能因为修正频繁而让整项任务更贵。

<!-- more -->

## 先描述任务，再筛选候选

知识问答关注证据忠实度，问数关注指标理解与结构化输出，客服关注响应速度和稳定表达。选型应该先写出关键成功条件，以及哪些错误不可接受，再用相同输入比较模型。

公开榜单适合缩小候选范围，不适合代替业务评测。测试集应包含真实语言风格、长短输入、模糊问题和异常情况，并保留不用于日常调参的独立样本。若模型需要工具或图像输入，应直接测试这些能力，而不是从文本榜单推断。

还要核对能力与使用条件：上下文范围、结构化输出支持、可用地区、数据处理政策、版本稳定性和许可。尤其自部署时，可下载权重不等于没有商业使用限制。

## 延迟是一条链，不是一个速度数字

用户体验既取决于首个有效反馈要等多久，也取决于最终任务完成时间。流式输出能够缓解等待，但不能让错误结果变正确，也不能弥补检索和工具调用中的长时间阻塞。

输入处理、排队、生成、网络与外部工具都会占用时间。长上下文通常增加输入处理及缓存开销，长输出则增加生成时间；复杂推理还可能引入额外计算。应测量端到端延迟及其分位数，而不是只看单人空闲测试时的每秒 Token 数。

同样，一条问数请求可能经过两次模型选择、一次 SQL 生成和一次修正。评估成本时要把完整调用次数、检索服务、数据库与失败重试都算进去，用“每个成功任务的成本”补充单次调用价格。

## API 与自部署分别把负担放在哪里

托管 API 减少了模型服务运维，但仍要面对速率限制、网络、版本变化和数据合规要求。自部署能增加基础设施控制权，却需要承担 GPU、推理服务、监控、升级和容量规划。它不是把调用费用简单换算成显卡价格就能决定的。

自部署的内存需求不仅有权重，还包括运行开销、激活及 KV Cache 等。并发和上下文长度改变后，容量表现也会变化。量化可能降低权重占用，但效果、硬件支持和吞吐收益需要实测，不能假设位宽减半就意味着整体成本减半。

批处理与连续批处理等技术可能提高吞吐，也可能改变单请求等待；前缀缓存可能减少重复输入的处理开销，但有适用条件。应围绕自己的请求分布做压测，而不是直接复用另一个项目的最大并发数字。

## 缓存与模型路由要认识语义边界

对重复、稳定的问题缓存答案可能有效，但个性化数据和实时库存不能只按问题文本复用。权限、知识版本、模型版本和业务有效期都可能影响缓存是否可用。前缀计算缓存与直接复用最终答案也不是同一种机制，不能混为一谈。

把简单任务交给较小模型、复杂任务交给更强模型，有时能降低成本；但路由器本身会误判，也带来额外调用。应检查困难样本是否被错误降级，以及切换模型后工具参数和格式是否仍符合要求。

降级也要诚实。数据库不可用时，可以解释暂时不能获取数据，不能为了保持回答率就改用模型猜一个数字。系统成功的含义应包含正确拒绝和可恢复失败，而不只是返回文本。

## 选型是一项持续回归工作

上线前保存模型、Prompt、工具和数据版本的基线，升级后运行同一组质量与安全测试，再用受控流量观察延迟和成本。模型名称未变也不意味着行为永远不变，依赖服务和业务数据同样会变化。

最终合适的模型，是在约束范围内稳定完成任务的模型。规模更大、窗口更长或功能更多，都只是候选优势，不是应用成功的充分条件。
