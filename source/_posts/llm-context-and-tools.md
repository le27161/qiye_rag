调模型时，很容易把所有问题都归结为“提示词还不够好”。但模型答错也可能因为资料过期、历史截断、工具参数错误，或者输出虽然合法却不符合业务。Prompt 是入口，不是整个应用。

<!-- more -->

## 好的上下文是选择结果，不是资料堆积

一次调用里的内容通常包括任务规则、用户问题、相关历史、外部资料和工具结果。它们有不同来源与可信程度。规则需要清楚、稳定；资料需要标明出处和时间；用户输入及网页内容则不能因为进入上下文就升级为系统指令。

有效的提示词往往只是把任务讲清楚：目标是什么，依据是什么，缺少信息时怎么办，输出应遵守哪些约束。少量示例可以展示期望风格，但不应把示例中的事实当成当前请求的真实数据。更多的提示词不一定更好，互相冲突的规则反而更难遵循。

上下文管理还涉及预算。对话很长时，应保留与当前问题有关的事实、约束和未完成事项，而不是机械保留全部聊天记录。摘要能压缩内容，也可能丢失细节，所以关键条件应单独结构化保存，必要时回查原文。

## 对话历史、任务状态和长期记忆不是一回事

对话历史记录说过什么，任务状态记录系统做到哪里，长期记忆则尝试跨会话保留仍然有效的信息。三者可以协作，但不能互相替代。用户上次查过华东销售额，不代表本次问题也默认使用华东；节点执行完成，也不意味着用户偏好应该永久保存。

长期记忆需要明确归属、有效期和删除方式。用户事实应与模型推断区分，敏感信息不该因为“可能以后有用”就无限保留。多用户应用还要隔离记忆与缓存，防止一个人的背景进入另一个人的回答。

检查点通常服务于执行恢复，向量库通常服务于语义检索，Redis 可能用作缓存或会话存储。它们是实现手段，不会自动决定记忆是否准确。记忆真正难的地方是哪些内容值得保存，以及什么时候应该忘记。

## 结构化输出把语言接到程序，但仍需验证

让模型返回符合 Schema 的对象，可以减少自由文本解析的脆弱性。例如把时间范围、地区和指标分别放入字段，程序就能在执行前检查缺失和冲突。若所用模型和接口支持原生结构约束，可以优先使用，并为拒绝、截断或解析失败设置正常分支。

然而，合法 JSON 只是语法层面的成功。`region` 可以是字符串，也仍可能填了不存在的地区；日期格式正确，也可能结束时间早于开始时间。业务值必须与受控字典、时间规则和用户权限核对。

工具调用进一步把对象变成行动请求。模型提出工具名及参数，宿主程序检查并执行，再把结果返回给模型。失败、超时和空结果都应有清楚结构，避免模型把一段错误信息当作真实事实继续分析。

## MCP 与 Skills 解决的是不同层面

MCP 提供客户端与服务端交换工具、资源等能力的协议约定，有助于减少不同工具接入方式之间的重复适配。它不等于 Agent，也不自动解决认证、权限和数据可信度；工具接上之后仍要由宿主决定是否允许调用。

Skills 一般指围绕某类任务组织的说明、参考资料和可选脚本等能力包，具体格式与加载机制依产品而异。它更接近“这类任务怎样做”的操作知识，而不是训练模型的新权重，也不是一个新的网络传输协议。

两者可以互补：技能说明如何整理一份报告，工具协议提供读取数据的入口，模型决定当下需要哪项能力，程序负责执行边界。不要因为某个内容被包装成工具或技能，就把里面的指令视为天然可信。

## 把正确责任放在正确位置

模型适合理解模糊请求、提取候选条件和组织表达；程序适合校验格式、计算日期、控制权限和执行工具；数据源负责提供可核对的事实。提示词可以描述这些分工，但实际约束必须在系统中存在。

当输出不稳定时，先定位是哪一层出了问题：没有明确任务，就改任务描述；拿错资料，就改检索；执行越权，就修权限边界；关键条件丢失，就修状态管理。这样比把所有补丁塞进同一段 Prompt 更容易维护。
