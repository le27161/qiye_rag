把一句话分成“FAQ”或“知识问答”，并不是意图识别最重要的产物。真正有业务意义的是：这次请求要不要检索、是否依赖历史、能不能直接返回标准答案，以及判断不确定时系统该如何保守处理。

<!-- more -->

## 先决定是否进入知识检索

“你好”“帮我联系人工”和“如何变更收款账户”，显然不需要走同一条路径。入口先处理确定性的问候、人工转接和范围边界，只有剩下的问题才进入检索意图判断。

还可以设置 FAQ 精确命中快路径，但“精确”的含义必须受控。安全的规范化可以处理首尾空格；不能为了提高命中率，把版本、金额、否定词也一并删除。“允许报销”和“不允许报销”绝不是同一个问题。

路由决定去哪里，检索意图决定怎么查，风险类别决定要多谨慎。这三个维度应分别保留，不要都挤进一个不断增长的枚举。

## 规则与模型擅长的事情不同

规则对确定表达有优势，容易定位和测试。例如明确的人工转接指令，通常没有必要再让模型猜测。

BERT 一类分类模型更适合覆盖表达变化，但需要标注数据、独立评测和部署维护。规则没命中，不意味着模型一定正确；模型给出高分，也不意味着可以越过权限或安全边界。

一种容易解释的组合，是先收集规则候选和模型候选，再由决策层按优先级、冲突情况及阈值确定最终结果。没有足够依据时，不强行给出“确定的 FAQ”，而进入更保守的知识检索，或者要求用户补充问题。

## 返回决策依据，不只返回一个 intent

下面是业务对象的设计示例，不依赖具体分类模型：

```python
from dataclasses import dataclass

@dataclass(frozen=True)
class IntentDecision:
    route: str
    retrieval_intent: str | None
    needs_rewrite: bool
    risk_category: str
    decision_score: float
    reasons: tuple[str, ...]
```

这样下游不仅知道“这是追问”，还能知道需要历史改写、是否存在规则与模型冲突，以及是否触发了保守兜底。分数应被称作决策诊断分；除非经过校准和验证，不宜直接显示成“识别正确概率”。

## source 推断不能变成授权

用户说“电脑重装后怎么连公司网络”，可以据此推断资料来源可能属于 IT。但推断的作用是缩小搜索范围，不是赋予用户访问 IT 私密资料的权利。

资料类别需要与当前场景的合法 source 列表匹配，并与认证身份允许的范围取交集。推断不确定时可以放宽到已授权范围，而不是越过授权边界去“多找一点”。

## 评测应该看决策后果

整体分类准确率不足以解释系统是否安全。还应分别检查：无需检索的问题有没有误入知识库；追问有没有触发改写；高风险问题有没有误走模糊 FAQ 直出；source 是否被错误收窄。

训练集和测试集还应避免同一原句的近义改写大量跨集合泄漏。否则模型看似学会了业务意图，实际只是记住了模板。

一个可靠的意图层，不是任何问题都给出漂亮标签，而是能解释判断，并让不确定性在下游产生真实的保护动作。
