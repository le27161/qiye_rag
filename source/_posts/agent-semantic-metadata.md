问数系统最难察觉的错误，往往没有报错堆栈。SQL 正常执行，表格也很整齐，但把退款前金额当成净收入，或者把订单明细行数当成订单数。修复这类问题，需要先修业务语义，而不是继续堆 SQL 示例。

## 表结构只能解释一半业务

字段类型告诉我们某列是日期还是数值，主外键提示数据怎样连接，但不会说明“有效订单”排除了哪些状态。语义层应同时保存物理结构和业务约定：表的粒度、字段含义、别名、受控维度值，以及指标的公式、时间字段、单位和过滤规则。

以客单价为例，可以约定为“同一时间范围内的有效支付金额，除以有效支付订单数”。这里每个修饰词都重要：是否扣除退款、按支付时间还是下单时间、跨币种怎样处理、零订单怎样返回，都要有定义。不能因为某字段叫 `order_quantity`，就默认它适合作分母。

更隐蔽的是粒度。订单表连接多行商品明细后，订单金额会被重复展开；直接 `SUM` 即便语法正确，也可能得到成倍的结果。语义层必须记录一对多关系，以及指标应在什么粒度先聚合。主外键名称相似只是线索，不能替代经过确认的关联关系。

## 字段、指标和维度值应分开检索

“看一下江浙沪的成交金额”里，成交金额倾向于指标匹配，江浙沪涉及维度值展开。可以使用 Qdrant 检索字段和指标，用 Elasticsearch 匹配字段值，再通过元数据库补齐详细信息。这种分工避免让同一种相似度同时承担所有语义任务。

一个字段可能按名称、描述和别名建立多条向量记录。这有利于召回，但需要区分向量记录 ID 与业务字段 ID。三个别名同时命中，仍然是一个字段，而不是三项不同证据。合并时应按稳定业务 ID 去重，并保留命中来源，方便排查为什么选中了它。

维度值索引也要节制。地区、品类、会员等级这样的受控值适合建立词表；把所有姓名、电话或订单号批量灌入检索系统，既增加成本，也扩大隐私暴露。高基数字段更适合经过权限检查的精确查询，而不是无差别建立语义索引。

## 从命中结果到可用上下文，还差一次补全

指标命中后应从权威元数据补回依赖字段；维度值命中后应补回所属字段及规范值。随后按表组织候选信息，加入必要的关联键和经过批准的 JOIN 路径。否则模型可能选对“地区”这个概念，却在没有关联键的情况下生成错误连接。

向量库的 payload 可以保存完整描述，减少查询次数，但它也可能滞后于元数据更新。更稳妥的约定是让检索索引带版本，关键公式与权限规则以权威存储为准。如果描述和公式不一致，系统应阻止查询或切换到已知一致版本，而不是把冲突一起塞给模型让它猜。

上下文太长时，可以让模型选取已有字段和指标的 ID，再由程序裁剪原始对象。返回了不存在的 ID 必须拒绝；关联键和指标必要依赖不能因为“看起来不相关”而删掉。这样模型参与的是选择，不是重新抄写整份 Schema，减少了描述和字段名被改写的机会。

## 语义层应该能被验证和演进

一个实用的指标变更记录可以包括负责人、定义版本、生效时间和对照查询。新增“净成交额”时，不只验证字段存在，还应准备包含退款、取消和跨日订单的小样本，人工计算期望结果，再与批准的 SQL 对照。

同义词也要区分适用范围。“收入”在经营分析与财务报表中可能不同，不能只靠全局别名覆盖。用户问题落入多个合理定义时，优先询问具体口径。一个明确的选择框，比系统悄悄猜中某个常用定义更容易建立信任。

因此语义层不是一次导表就完成的配置文件，而是数据团队与应用之间的契约。它的质量决定了模型能够在多大范围内可靠生成查询，也决定了出现争议时能否定位到一个具体定义。
