增量入库看起来只需要问一句：“这个文件变了吗？”但文件内容、解析参数和模型都可能改变结果。若把这些变化压缩成一个含义不明的 fingerprint，系统就可能错误地跳过重建，或者覆盖仍被历史版本使用的片段。

## 元数据指纹不等于内容哈希

路径、大小和修改时间适合做低成本变更筛选，但即使最后对它们计算 SHA256，得到的也仍然是元数据摘要，不是文件内容摘要。

相同大小、被保留的修改时间，可能让内容变化被漏掉；单纯移动或触碰文件，也可能造成不必要重建。严格判断内容一致时，应读取文件字节计算摘要，或者利用受信任存储系统提供的内容版本标识。

```python
from hashlib import sha256
from pathlib import Path

def content_digest(path: Path) -> str:
    digest = sha256()
    with path.open("rb") as source:
        for block in iter(lambda: source.read(1024 * 1024), b""):
            digest.update(block)
    return digest.hexdigest()
```

大文件可以先用快速指纹减少读取，再在需要严格确认时算内容摘要。两种策略都合理，前提是名字与承诺一致。

## 稳定 ID 首先要定义稳定的范围

文件身份、内容修订和片段身份不是一回事。路径可以标识逻辑文件，内容摘要标识某次修订，片段 ID 则可能由租户、逻辑文件、修订、切分配置和块位置组合产生。

若同一路径的第 3 块在更新后沿用旧主键，并被直接覆盖，那么历史版本引用的旧内容也会一起丢失。需要保留多版本时，稳定应该意味着“相同修订重复处理结果一致”，而不是“无论内容如何变化永远用一个 ID”。

输入拼接也有歧义。`ab + c` 与 `a + bc` 不应生成同一个身份；可用规范化 JSON 数组或有长度信息的编码构造摘要，不要简单连接字符串。

## 处理配置也是内容产物的一部分

解析器版本、父子块策略、归一化规则、Embedding 修订和表格清洗方式，都应纳入处理契约。源文件没变，契约变化也可能让旧向量不再适用。

把这些配置规范化序列化后保存摘要，可以解释某个文件为什么被重建。配置摘要不是安全密钥，不应把真实 API Key 混进去，更不能把它当作保密手段。

## 小工具也会形成系统约束

持久化时间统一保存带时区的 UTC，展示时再转换；不要混用无时区本地时间和 UTC。版本排序最好依赖明确序号，不只依赖文件名中的时间字符串。

报告写入应尽可能采用临时文件后原子替换，避免状态页读到半截 JSON；但原子替换不能替代并发控制。关键版本和 Manifest 状态适合存进有事务约束的控制面，报告文件只作为审查产物。

外部输入边界适合使用 Pydantic 校验，已验证的内部对象可用 dataclass 表达。数据库连接池可以惰性创建，但 schema 初始化应有明确入口，重试写入还需要幂等键，不能因为重连成功就重复提交。

这些工具单独看都不复杂，难的是全系统遵守同一套约定。基础契约清晰以后，增量构建、回滚和排错才能得到可信答案。
