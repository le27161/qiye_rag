当模型回答不好时，“换提示词”“加知识库”“做 Agent”“微调一下”听起来都可能有用。但这些手段改变的是不同环节。如果问题根源是没有实时库存，把表达风格训练得更统一，并不会让库存数字变新。

<!-- more -->

## 先把失败原因说具体

“模型不够聪明”很难指导改进。更有用的描述是：不知道内部制度、把用户条件漏掉、输出格式不稳定、算错数字、访问工具失败，或者执行了不应该执行的动作。不同错误需要不同证据和修复方式。

可以先保留一组真实问题及其期望结果，记录现有模型在相同输入下的表现。后续每次只改变一类因素，再比较效果。否则同时换模型、改 Prompt、补资料之后，虽然结果变好，也难以知道投入到底花在了哪里。

| 主要缺口 | 优先考虑的手段 | 仍需系统承担的责任 |
| --- | --- | --- |
| 任务或输出要求不清 | 明确 Prompt、示例与 Schema | 业务校验与失败处理 |
| 缺少内部或最新资料 | RAG、数据库查询等外部来源 | 权限、更新与证据核对 |
| 需要执行多步行动 | 工具与受控工作流，必要时 Agent | 授权、预算、幂等与停止条件 |
| 稳定任务中反复出现行为偏差 | 在基线与数据成熟后评估微调 | 数据质量、独立评测与回归 |

这些只是常见起点，不是互斥分类。同一个问数系统可以检索业务定义，再调用数据库，并使用结构化输出约束中间结果。

## Prompt 适合先建立清楚的任务契约

任务说明、输入边界、少量示例和预期格式，常常足以改善摘要、分类和信息抽取。若原文已经包含答案，就没必要为了抽取信息额外搭建一套知识库。先做简单方案，可以得到成本较低、比较清楚的基线。

但 Prompt 不是安全边界。写“不要泄漏其他部门数据”不能替代数据权限；写“必须准确计算”不能替代计算工具。模型遵循规则的能力与系统是否真正限制能力，是两个不同问题。

## RAG 改变的是可获得的证据

内部文档、频繁更新的规则、需要引用来源的回答，适合通过检索把相关资料送进上下文。它的难点包括内容解析、检索、版本管理与权限，而不仅是建一个向量库。

RAG 也不会保证生成忠于证据。应检查召回是否命中、资料是否冲突、答案是否正确引用，以及证据不足时能否拒答。对于实时结构化数据，直接查询受控数据库可能比把所有行转成文档更合适。

## Agent 改变的是执行过程中的决策空间

当任务需要选择工具、根据结果继续操作或在多个步骤间调整路径时，可以考虑 Agent。路径确定时先用固定工作流，只有不确定路径确实带来收益时才扩大模型决策权。更多自主性会带来更多预算、追踪和安全约束。

比如问数 Agent 可以决定候选指标，却不应该决定用户权限；可以尝试修正字段引用，却不能绕过只读限制。它的价值不是“什么都能做”，而是能在明确边界内把语言意图落实为行动。

## 微调只保留一个必要认识

微调会用样本继续训练并更新可训练参数，更适合明确、重复、可评测的行为或任务适配，而不是用来记住每日变化的库存。SFT 描述利用输入与参考答案训练的方式；LoRA 是参数高效适配方法，两者可以组合。是否值得采用，应比较更好的 Prompt、候选模型与微调方案在独立测试集上的质量和成本，而不是只看训练损失下降。

## 方案最终要回到成本和维护

简单调用更容易维护，复杂检索需要知识治理，自主工具调用需要执行治理，训练则增加数据与模型版本管理。每一层都应解决一个已经被验证的问题，而不是为未来可能出现的需求提前堆叠。
