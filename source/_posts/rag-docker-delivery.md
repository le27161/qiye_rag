“我电脑上可以运行”与“别人按文档能部署成功”，中间隔着模型目录、容器网络、持久化数据和初始知识版本。Docker 可以固定一部分运行环境，但不会自动补齐这些依赖。

<!-- more -->

## 镜像与运行数据分开管理

API 代码适合打进镜像，本地模型和业务资料则可以通过受控挂载提供。模型体积大、更新节奏不同，不必每次改几行 Python 都重新打包。

项目相对路径通常比 `D:/某个个人目录` 更便于迁移。例如把项目 `models` 挂到容器 `/app/models`，应用只使用容器内部路径。挂载要核对目录是否存在、权限是否正确，以及是否需要只读。

数据库、向量存储及对象存储应持久化。`docker compose down` 与带 `-v` 的操作有本质区别：后者可能删除命名卷和业务数据，不能当作常规重启步骤。

## localhost 的含义取决于你站在哪里

在宿主机中，`localhost` 指宿主机；在 API 容器中，它指 API 容器自己。API 连接同一 Compose 网络中的数据库，通常应使用服务名，而不是宿主机回环地址。

```text
宿主机调试程序 → 已发布到宿主机的端口
API 容器       → mysql / redis / milvus 等服务名和容器端口
```

数据库没有必要全部暴露到公网。确需宿主访问时，应明确绑定地址、防火墙与认证，而不是认为“放进 Docker 就自动安全”。

## 初次入库要能独立于 API 完成

如果 API 启动要求存在 active 知识版本，而入库命令又只能通过已启动 API 执行，就形成了死循环。

部署应允许一次性任务复用 API 镜像，等待基础服务可用后，直接运行项目入库入口，创建并检查初始版本，再启动问答 API。任务失败时保留报告和已有数据，不应立即重置集合掩盖原因。

先完成配置解析，再确认服务健康，然后验证真实业务，是三个不同层次。配置合法不等于端口可达，端口可达也不等于知识可检索。

下面仅是通用排查命令，需要在包含实际 Compose 配置的 RAG 项目中运行；本博客仓库不包含这些服务：

```powershell
docker compose --env-file .env.compose config --quiet
docker compose --env-file .env.compose ps
docker compose --env-file .env.compose logs --tail 100 api
```

`config --quiet` 适合检查解析错误，避免完整渲染配置时把已插值的敏感值打印出来。

## 构建成功仍需业务冒烟

最低限度的验收，应确认当前版本存在、集合可查、本地模型可推理，并真实完成一次 FAQ、一次文档引用和一次无资料回答。

如果更新环境变量，普通 `restart` 通常不会重新创建容器并注入新值，需要根据 Compose 配置重新创建服务。如果修改的代码已经固化在镜像里，则要重新构建，而不是只重启旧镜像。

依赖缺失要在镜像中验证，不能用宿主机“已经 pip install”作为证据。模型路径错误则分别检查宿主目录、挂载目标与应用设置，别只看一处。

## 日常更新与破坏性重建分开

资料变更优先发布新知识版本；schema 不兼容才考虑受控迁移或新集合。删除旧集合会连带影响历史版本与回滚，必须先做备份和明确确认，不能把重建当成通用修复按钮。

可交付的 RAG 项目，至少应该提供依赖锁定、无真实密钥的配置模板、模型准备说明、初次入库入口、冒烟步骤及备份回滚策略。真正的交付完成，是在另一台机器上也能解释每一步为什么成功。
