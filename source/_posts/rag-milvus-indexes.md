检索变慢时，最容易想到的是调整 HNSW 的 `ef`。但如果集合没有正确加载、实际执行的并非预期索引，或者时间主要花在 Embedding 上，调整这个参数只会增加困惑。索引调优之前，应该先证明问题确实发生在向量搜索阶段。

<!-- more -->

## 给近似检索准备一把尺子

FLAT 直接比较所有候选向量，计算量随着数据规模增长，但在给定度量下能提供精确排序，因此适合作为小规模对照基线。

ANN 索引的目标不是数学上永远找到同一组最近邻，而是在允许少量漏召回的前提下降低延迟。没有精确基线和标注样本，就难以判断一次优化是“更快且可接受”，还是“更快但把答案丢了”。

还要把 ANN recall 与业务 Recall@K 分开。前者比较近似结果与精确近邻是否一致；后者检查业务上正确的证据是否进入候选集。精确找到向量最近邻，也不保证它就是正确业务证据。

## 三类方案，本质是不同的搜索捷径

| 方案 | 缩小搜索范围的方式 | 主要代价 |
| --- | --- | --- |
| FLAT | 不缩小，逐一比较 | 大规模查询计算量高 |
| IVF | 先找邻近聚类，再搜其中向量 | 需要在搜索桶数与召回之间权衡 |
| HNSW | 沿分层邻接图逐步接近目标 | 图结构需要额外内存与构建成本 |

量化索引进一步压缩向量表示，节省空间和计算，但可能损失精度。不存在只按“百万条以内用什么”就能确定的通用答案：向量维度、过滤选择性、更新频率和并发量都会改变结果。

## HNSW 的三个旋钮不是一回事

`M` 影响图的连接规模，通常会改变内存及搜索能力；`efConstruction` 影响建图阶段的候选探索，主要体现为构建成本和图质量；搜索期 `ef` 控制一次查询探索的宽度。

因此，线上临时调整搜索宽度，与重新建一个更好的图，是两种不同操作。下面仅展示 PyMilvus 风格的参数结构，字段名和可选项需核对实际客户端及服务端版本：

```python
index_params = {
    "index_type": "HNSW",
    "metric_type": "L2",
    "params": {"M": 16, "efConstruction": 160},
}
search_params = {"metric_type": "L2", "params": {"ef": 64}}
```

这些数字是实验起点，不是最佳实践保证。应让搜索宽度与请求的候选数量相匹配，并在真实权限过滤条件下测试。

## 改配置，不代表旧集合已经变了

索引参数写进 Python 后，已有集合不一定自动重建。先读取实际 schema 和 index description，确认向量维度、metric、索引类型及文本分析配置。

同样，已用 L2 创建的索引，不应在查询时随意切换成 COSINE。即使归一化向量下二者排序有数学关系，数据库接口仍要求度量兼容。

更稳妥的调优过程，是固定一份查询集，分别测编码、数据库搜索、重排耗时，再逐项比较召回、P95 和内存。涉及索引重建时，优先建立可验证的候选集合，避免直接删除仍在服务的线上数据。
