最危险的知识库泄漏，不一定表现为系统直接返回另一家公司的文件。它也可能只是把对方文档里的一个金额写进答案，而页面上没有显眼的来源。防止这种问题，必须在证据进入模型之前完成隔离。

<!-- more -->

## 数据范围来自身份，而不是请求自报

请求可以提出“只查 IT 资料”的偏好，但不能自己声明 `tenant_id` 或管理员角色就获得授权。后端应从经过验证的身份中解析租户、数据集与角色，再与请求条件取交集。

常见范围包含租户、数据集、可见级别、允许角色、业务 source 和知识版本。它们不是互相替代的条件；缺失关键授权字段时，应明确拒绝或使用经过设计的最小权限，而不是默认扩大搜索。

可见级别可以设计为“高级别包含低级别”，但必须明确角色条件如何叠加。更高级的可见级别，不应自动绕过某份文档独立设置的角色限制。

## 在召回时过滤，不要拿到以后再删

先跨租户检索、再在应用里删除无权候选，会浪费 Top-K，也可能让数据进入日志、重排输入和缓存。更可靠的是在 dense、sparse、FAQ、文档及父块恢复等所有分支使用一致范围。

过滤表达式应由受控构造器生成。source 先与场景白名单核对，字符串值再按数据库表达式规则编码；客户端支持参数绑定或表达式模板时优先使用。不能把任意前端字符串直接拼进条件。

测试不应只检查表达式“长得对不对”，还要在真实小集合中确认：租户 A 的用户确实看不到 B 的结果，异常引号和反斜杠不会改变条件结构。

## 缓存键也需要同样的范围

如果检索结果缓存只使用问题文本作为键，即使数据库过滤完全正确，也可能从缓存读到另一个用户的候选。

一个检索缓存键通常应包含：规范化查询、租户与数据集、有效权限摘要、source、版本视图、检索计划，以及模型和排序配置摘要。下面只演示稳定编码方式：

```python
import hashlib
import json

def make_cache_key(payload: dict) -> str:
    canonical = json.dumps(
        payload, ensure_ascii=False, sort_keys=True, separators=(",", ":")
    )
    return hashlib.sha256(canonical.encode("utf-8")).hexdigest()
```

调用者需要先把角色、source 等集合排序去重；也要决定字符串规范化规则，不能为了命中率随意去掉否定词或编号。

查询向量缓存与候选缓存的依赖并不相同。前者主要依赖文本和编码契约；后者还依赖权限、知识版本及检索参数。安全策略要求租户隔离时，即使内容相同，向量缓存也可以分命名空间管理。

## 缓存 epoch 是失效控制，不是第三份结果

一种轻量方案是在进程内短暂缓存 epoch，在 Redis 保存查询向量和候选，在 MySQL 维护命名空间与 epoch。这里 MySQL 承担控制面，不是又存了一份检索结果。

切换版本或修改授权后，提升对应 epoch，让新请求使用新键。但进程内 epoch 快照有传播窗口，不能依赖较长 TTL 实现紧急权限撤销。安全敏感更新需要更及时的通知或重新授权。

普通 LLM 自由生成答案包含更多上下文依赖，直接缓存风险更高。若要缓存，必须纳入完整身份、历史、策略和证据版本；第一版优先缓存可解释的中间对象通常更稳妥。

缓存命中率是性能指标，不是质量指标。最重要的是，命中时依然遵守当前授权。
