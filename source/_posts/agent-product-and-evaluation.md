用户不会因为后端采用了状态图就信任一个数字。他更关心“这是哪段时间的数据”“为什么和报表不一样”“刚才失败有没有继续执行”。问数系统的交付，不应停在 SQL 执行成功，而要让结果及其边界可以被理解。

## 输出结果时，也输出问题的解释

对“本月销售额”这样的输入，结果页应展示实际时间范围、业务时区、指标名称和数据更新时间。若默认只统计已支付订单，就把默认条件放在可见位置。系统采用了假设，用户才有机会纠正它。

表格是主要事实载体，文字解释是辅助。没有行不等于数值为零，空值也不等于数据库失败。结果被截断时，要明确标注“仅展示前若干项”，不能将局部合计说成整体表现。金额的币种、小数位和数量单位也应来自指标定义，而不是让模型自行添加。

“为什么下降”尤其需要克制。查询显示两个时间段的差异，并不自动证明因果。可以提出需要继续验证的维度、返回分组对比，但不能仅凭一个数字就断言是营销活动失效。问数与归因分析的能力范围应在产品上区分。

## SSE 适合进度，但不负责所有可靠性

查询过程可以通过 FastAPI 和 SSE 返回。单次请求、服务端不断发送状态的场景很适合这种传输：前端可以依次展示条件解析、检索完成、查询执行和最终结果，而不必让用户盯着一个无限旋转的图标。

接口可以保持薄层：验证输入与身份，调用查询服务，再由服务运行工作流。检索客户端和连接池由应用生命周期管理；具体数据库会话按请求或任务隔离。不要为了方便把所有节点需要的对象都放进图状态，更不要跨并发节点共享不安全的会话。

事件最好有稳定类型、请求 ID 与明确终态，例如 `progress`、`result`、`error`、`done`。流开始后 HTTP 响应头已经发出，后续失败通常需要通过错误事件表达，不能指望再改成另一个 HTTP 状态码。客户端也应把连接中断与业务完成区分，避免把半段文本当最终结果。

浏览器原生 `EventSource` 与基于 `fetch` 读取 POST 流的接口方式不同，鉴权和参数传递要按选定方式设计。SSE 本身不保证取消数据库查询、断线续传或事件去重；这些都需要任务状态、事件编号和数据库驱动能力配合。

## 一条 Trace 应能解释哪里出了问题

同一次问数的请求 ID 应贯穿接口、图节点、检索与数据库调用。记录每步耗时、候选对象数量、元数据版本、模型与 Prompt 版本、修正次数和终止原因，才能区分“检索没找到字段”和“数据库执行太慢”。

日志不必保存所有原始数据。SQL 中可能包含个人信息，结果集可能包含业务敏感数字；完整 Prompt 也可能含内部结构。应采用分级访问、脱敏和保留期限，把必要审计与广泛可见的运行日志分开。

流式进度同样不宜泄漏内部信息。给普通用户展示“正在核对查询条件”通常足够；数据库实例名、堆栈和凭据不应该随着调试事件流到浏览器。可观测性是帮助授权人员排障，不是把系统内部全部公开。

## 评测不只比较 SQL 字符串

两条写法不同的 SQL 可能算出同一个结果；两条只差一个过滤条件的 SQL，也可能在某批数据上碰巧结果相同。因此评测应同时检查结构与业务结果，并使用能暴露错误的固定样本，例如一笔退款订单、一个跨月订单和一组一对多明细。

一份问数评测集应覆盖明确查询、同义表达、歧义口径、多轮追问、越权请求、无数据和超时场景。分别观察字段与指标召回、条件解析、执行成功、结果正确、拒绝与澄清是否合理，再看端到端完成率、延迟和成本。

这些指标会暴露不同问题。执行成功率高而口径正确率低，应回到语义层；模型修正频繁，应检查生成上下文与校验反馈；安全拒绝多也不一定是坏事，可能说明测试集包含了本来就不该执行的请求。一个可用产品需要解释这些差异，而不是只追求“有答案”的比例。
